보안 점검을 하다 보면 누구나 한 번쯤 이런 걸 해본다.

```bash
# "위험한 eval() 쓰는 데를 다 찾아줘"
grep -rn "eval(" .
```

그리고 곧 실망한다. 결과에는 진짜 문제가 되는 코드도 있지만, 그냥 문자열 안에 `"eval("`이라고 적힌 로그 메시지, 주석 처리돼서 실행되지도 않는 옛날 코드, 심지어 변수 이름에 `eval`이 들어간 애먼 줄까지 죄다 딸려 나온다. 반대로 정작 잡았어야 할 `const run = eval; run(userInput)` 같은 우회는 놓친다.

왜 이럴까? `grep`은 코드를 **글자 그대로의 텍스트**로만 보기 때문이다. `grep`에게 소스 파일은 그냥 긴 문자열일 뿐, "이게 함수 호출인지 주석인지"를 구분할 능력이 없다. 하지만 우리가 보고 싶은 건 텍스트가 아니라 **의미**다. 그래서 쓸데없는 경보는 잔뜩 뜨는데, 정작 잡아야 할 건 놓친다.

**Semgrep이 바로 그 틈을 메워주는 도구다.** 이름부터가 그렇다. `grep`은 그대로 두고 앞에 "의미"를 뜻하는 `sem`(semantic)을 붙였다. 이름 그대로 "의미를 아는 grep"인 거다.

---

## 텍스트가 아니라 '구조'를 본다

Semgrep이 grep과 결정적으로 다른 점은, 코드를 읽을 때 먼저 **파싱**을 한다는 것이다.

파싱이란 소스 코드를 컴파일러가 이해하는 방식, 즉 **문법 트리(AST, 추상 구문 트리)** 로 바꾸는 과정이다. 이 트리 위에서는 "이건 함수 호출이고, 저건 문자열 리터럴이고, 그건 주석"이라는 게 명확히 구분된다.

Semgrep은 우리가 찾고 싶은 **패턴도 똑같이 트리로** 바꾼 다음, 트리끼리 맞춰본다. 그래서 다음과 같은 표면적인 차이에 전혀 흔들리지 않는다.

- 공백이나 줄바꿈이 어떻게 들어가 있든 (`eval(x)`나 `eval(\n  x\n)`나 같은 것으로 본다)
- 변수 이름이 무엇이든
- 주석 안에 들어 있는 코드는 아예 코드로 치지 않는다

쉽게 말해 grep은 글자를 비교하고, Semgrep은 문장 구조를 비교한다.

---

## 규칙이 그냥 그 언어 코드처럼 생겼다

여기까지만 들으면 "그거 컴파일러나 정적 분석기 다 하는 거 아냐?"라고 할 수 있다. Semgrep의 진짜 매력은 **그 패턴을 우리가 직접, 아주 쉽게 쓸 수 있다**는 데 있다.

보통 정적 분석 규칙을 커스터마이징하려면 그 도구의 내부 AST API를 배워야 한다. 진입 장벽이 높다. 반면 Semgrep 규칙은 **그냥 우리가 찾고 싶은 코드를 그 언어로 써주면** 된다.

예를 들어 자바에서 "신뢰할 수 없는 데이터를 역직렬화하는" 위험한 패턴을 찾는다고 하자. (역직렬화 취약점은 실제로 대형 보안 사고의 단골 원인이다.)

```yaml
rules:
  - id: java-insecure-deserialization
    languages: [java]
    severity: ERROR
    message: "신뢰할 수 없는 입력을 ObjectInputStream으로 역직렬화하고 있습니다."
    pattern: |
      ObjectInputStream $OIS = new ObjectInputStream(...);
      ...
      $OIS.readObject();
```

`pattern` 부분을 보면 거의 평범한 자바 코드다. 딱 두 가지 특별한 문법만 알면 된다.

첫째, **`$OIS` 같은 `$`로 시작하는 이름은 '메타변수'** 다. "여기엔 뭐가 오든 상관없다"는 뜻이다. 다만 같은 이름이 두 번 나오면 "둘은 같은 것이어야 한다"는 조건이 붙는다. 위 예시에서 `$OIS`가 두 번 나오는 건 "위에서 만든 그 스트림을, 아래에서 실제로 `readObject()` 하는가"를 확인하기 위해서다.

둘째, **`...`(점 세 개)은 '그 사이에 무슨 코드가 있어도 좋다'는 와일드카드**다. 스트림을 만든 줄과 실제로 읽는 줄 사이에 다른 코드가 몇 줄 끼어 있어도 상관없이 잡아낸다.

정규식으로 이걸 표현하려면 머리가 아프지만, 그 언어를 아는 개발자에게는 이 방식이 훨씬 자연스럽다. 덕분에 팀은 자기 회사에만 있는 안티패턴 — 이를테면 "우리 내부 인증 유틸을 건너뛰고 직접 DB를 찌르는 코드" — 도 몇 줄짜리 규칙으로 직접 잡을 수 있다.

---

## 언어가 섞여 있어도 도구 하나면 된다

현실의 프로젝트는 대개 한 가지 언어로만 되어 있지 않다. 백엔드는 Java/Spring, 프론트는 TypeScript, 스크립트는 Python, 모바일은 Kotlin 식으로 섞인다.

만약 언어마다 다른 정적 분석 도구를 붙인다면, 도구마다 설치법도 다르고 출력 형식도 달라서 그걸 하나로 모으는 데만 한참이 걸린다. Semgrep의 실용적인 강점이 여기 있다. **이 언어들을 엔진 하나로 전부 훑는다.**

실제 스캔 명령도 놀랄 만큼 단순하다.

```bash
semgrep scan \
  --config p/default \   # 저잡음 커뮤니티 기본 룰셋
  --json --quiet \
  --metrics off \        # 외부로 데이터 전송 금지
  --exclude node_modules --exclude venv ... \
  <대상 경로>
```

이 짧은 명령 안에도 실무에서 중요한 결정이 몇 개 숨어 있다.

**`--config p/default`.** Semgrep은 커뮤니티가 만든 수천 개의 규칙을 공개 저장소(Registry)에 올려두고 있다. 그걸 다 켜면 경보가 쏟아진다. `p/default`는 그중에서 "오탐이 적고 신뢰할 만한" 규칙만 골라 담은 기본 팩이다. 일단 여기서 시작하고, 의료기기처럼 더 엄격한 도메인이라면 나중에 OWASP 팩이나 언어별 보안 팩을 추가로 얹으면 된다.

**`--metrics off`.** Semgrep은 기본 설정이면 익명 사용 통계를 자기네 서버로 보낸다. 평소엔 문제없지만, FDA 규제 대상 같은 환경에서는 **어떤 데이터도 바깥으로 나가면 안 된다.** 그래서 이 스위치를 꺼서 아예 통신을 막는다.

**제외 디렉터리.** `node_modules`, `venv`, `dist`, `build` 같은 폴더에는 우리가 짠 코드가 아니라 남의 라이브러리나 빌드 결과물이 들어 있다. 여기까지 스캔하면 남의 코드에서 나온 수천 건이 리포트를 뒤덮어서, 정작 우리가 고쳐야 할 문제가 파묻힌다. 그래서 처음부터 빼고 본다.

## 심각도는 한 번 더 걸러서 받는다

스캐너가 "문제 발견!"이라고 외칠 때, 그게 다 같은 무게는 아니다. 당장 서비스를 뚫을 수 있는 치명적 결함도 있고, "이렇게 쓰면 좀 지저분하다" 정도의 지적도 있다. 이 둘이 같은 색으로 표시되면 리포트를 믿기 어려워진다.

그런데 Semgrep은 심각도를 딱 세 단계(`ERROR / WARNING / INFO`)로만 내보낸다. 표현력이 부족하다. 그래서 이걸 받아서 한 번 더 다듬는 게 좋다.

먼저 세 단계를 내가 쓰는 등급 체계로 옮긴다.

```
ERROR   → HIGH
WARNING → MEDIUM
INFO    → LOW
```

그다음이 핵심이다. Semgrep 규칙에는 보통 `impact`(터졌을 때 얼마나 아픈가)와 `confidence`(이 탐지가 얼마나 확실한가)라는 메타데이터가 붙어 있다. **이 둘이 모두 HIGH일 때만**, 원래 HIGH였던 걸 최상위인 CRITICAL로 올리는 식이다.

"영향도 크고, 오탐일 가능성도 낮다" — 이 두 신호가 겹칠 때만 최고 등급을 준다. CRITICAL을 함부로 남발하지 않으니, 리포트에 CRITICAL이 뜨면 받는 사람도 그제야 진짜 긴장하게 된다.

## 장점과 단점

한 도구가 모든 걸 해주지는 않는다. Semgrep이 어디까지 커버하는지 그 선을 알아두는 편이 오히려 이 도구를 잘 쓰는 길이다.

**장점은 넓고 빠르다는 점이다.** 여러 언어를 한 번에 보고, CI에 물려도 부담이 없을 만큼 빠르며, 조직 고유 규칙을 붙이기도 쉽다. 발견한 문제에 CWE·OWASP 같은 표준 분류를 달아주기 때문에 나중에 리포트를 정리하기도 편하다.

**단점은 깊이 있는 추적에 약하다는 점이다.** 기본 Semgrep은 한 파일 안의 패턴을 잡는 데 강하다. 반대로 사용자 입력이 여러 함수와 파일을 거쳐 위험한 지점까지 흘러가는 복잡한 데이터 흐름(taint) 추적은 상용 Pro 쪽이 훨씬 낫다. 인증 우회나 세션 관리 결함처럼 실제로 실행해봐야 드러나는 문제도 소스만 읽는 SAST의 몫이 아니라, 요청을 직접 보내보는 DAST 도구가 맡는다.

그래서 Semgrep은 만능이 아니라 **파이프라인의 첫 관문**으로 두는 게 맞다. 넓고 빠르게 훑어 눈에 띄는 문제를 초반에 걸러내고, 더 깊은 검사는 뒷단계에 넘기면 된다.

## 그다음 이야기: 결과를 어떻게 넘길까

Semgrep은 `--json`을 붙이면 자기만의 상세한 JSON을 내놓는다. 문제는, 대개 파이프라인에는 Semgrep만 있는 게 아니라는 점이다. 다른 스캐너도 있고, 그 결과는 웹 대시보드로도 가고 규제 제출용 증거 문서로도 가야 한다.

도구마다 출력 형식이 다르면, 그걸 받아 쓰는 쪽은 도구 수만큼 파서를 만들어야 한다. 금방 감당이 안 된다. 그래서 보통은 모든 스캐너의 결과를 **하나의 표준 형식으로 정규화**한다. 그 표준이 바로 SARIF인데, 이건 그것대로 이야깃거리가 많아 따로 정리해 뒀다.
